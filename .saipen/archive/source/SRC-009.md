[P0] [CORE-001] src/config/config_storage.cpp::deserialize_json/load_from_file/save_to_file + src/app/application.cpp::initialize/shutdown/save_config

EVIDENCE:
- `AppConfig::kCurrentSchemaVersion` is 10 at src/config/app_config.h:43.
- `ConfigStorage::deserialize_json()` accepts any numeric `schema_version` verbatim at src/config/config_storage.cpp:130-132. There is no `schema_version > kCurrentSchemaVersion` rejection anywhere in src; the source-wide schema search finds only historical lower-bound/introduction checks.
- `AppConfig::validated()` at src/config/app_config.cpp:5-12 repairs only `schema_version <= 0`; a future schema remains accepted.
- `ConfigStorage::serialize_json()` serializes the fields understood by this build and then unconditionally writes `root["schema_version"] = AppConfig::kCurrentSchemaVersion` at src/config/config_storage.cpp:112-116. Unknown fields from a newer writer therefore cannot survive a save.
- `Application::initialize()` converts the load result directly into the live mutable `AppConfig` at src/app/application.cpp:211-218, while `Application::shutdown()` unconditionally calls `save_config()` at src/app/application.cpp:899-909.
- Consequently, a syntactically valid schema-11+ config can be opened by this schema-10 binary and then rewritten as schema 10 on an otherwise uneventful shutdown, dropping every unknown future field.
- A second deterministic destructive route already exists around malformed recovery: `load_from_file()` returns release defaults after a failed `.corrupt` backup at src/config/config_storage.cpp:406-421. The T-38 regression at tests/test_config.cpp:1724-1775 explicitly proves that in this failure case the malformed original remains intact after `load_from_file()`. The full Application lifecycle then loses that protection because shutdown treats the returned defaults as ordinary writable state and replaces the original through `save_config()`.
- Read/open failures at src/config/config_storage.cpp:388-400 are likewise collapsed into an ordinary default `AppConfig`, so the API carries no provenance telling Application whether persistence is safe.
- ROADMAP/QUALITY_GATES.md explicitly requires that failed persistence/recovery must not destroy previous user configuration; the current composition violates that invariant.

DEFECT:
`load_from_file()` erases the distinction between SAFE-TO-WRITE states and PROTECTED source states. Missing config, successfully migrated config, unreadable existing config, unsupported future config, malformed config with successful backup, and malformed config whose backup FAILED all ultimately become an `AppConfig`. Application therefore cannot enforce the preservation boundary and its unconditional shutdown save can destroy the only copy of user data. The future-schema path additionally performs an implicit destructive downgrade from a newer schema to 10.

REPAIR:
- Replace the bare `AppConfig load_from_file(...)` lifecycle contract with a status-bearing result, for example `ConfigLoadResult { AppConfig config; LoadStatus status; bool persistence_allowed; }`. Exact naming is implementation choice; the invariant is not.

- Reject `schema_version > AppConfig::kCurrentSchemaVersion` before applying current-schema semantics. Treat it as valid-but-unsupported, not corrupt: do not rename it to `.corrupt`, do not rewrite it, and log the exact detected/current versions.
- Permit normal writes for MissingFresh, LoadedCurrent, LoadedMigrated, and MalformedBackedUp because the original malformed bytes have been secured.
- Disable persistence for MalformedBackupFailed, UnsupportedFutureSchema, and ReadFailure unless/until an explicitly safe recovery action occurs.
- Store the load safety state in `Application::Impl`; make every `save_config()` path, including shutdown, respect it. A blocked save must be explicit in logs and must never touch the protected source.
- Preserve all existing <=10 migration semantics and successful `.corrupt` recovery behavior.
- Do not solve this by blindly copying unknown JSON members into schema 10; an older binary cannot safely claim compatibility with semantics it does not understand.

VERIFY:
