[P0] [CORE-001] src/config/config_storage.cpp::ConfigStorage::load_from_file_result / filesystem existence probe
EVIDENCE:
- `load_from_file_result()` creates `std::error_code ec` and immediately evaluates `if (!std::filesystem::exists(path, ec))`.
- The `ec` value is never checked.
- Every false result therefore enters `MissingFresh` with `persistence_allowed = true`.
- The same function explicitly treats an existing-but-unreadable file as `ReadFailure` with persistence disabled, proving that inability to establish source state is intended to be fail-closed.
- Existing CORE-001 tests cover open/read failure and the forced-read-failure seam, but do not cover an error from the filesystem status/existence probe.
DEFECT:
A filesystem metadata error is conflated with a proven-absent configuration. `std::filesystem::exists(path, ec)` can report false while also setting `ec`; ProTrail then installs Release Defaults and marks the source writable. If the original config actually exists and the transient/status error clears before a subsequent save, the ordinary persistence path is authorized to replace the user's only config with defaults. This reopens the exact protected-source data-loss class that CORE-001 otherwise attempts to close.
REPAIR:
- Split the probe into three states: exists, definitely missing, and probe error.
- Check `ec` before classifying a false existence result.
- On probe error, return protected provenance equivalent to `ReadFailure`: Release Defaults may be used only as runtime fallback, `persistence_allowed = false`, original path untouched, and an explicit error logged.
- Emit `MissingFresh` only when absence was established without an error.
- Add a deterministic filesystem-status/error seam or a narrowly injectable probe so this branch can be regression-tested without relying on OS timing/permissions.
- Preserve all existing successful MissingFresh, malformed-backup, migration, and current-schema behavior.
VERIFY:
- Add a test where the existence/status probe returns an error for a path representing an existing config; assert status is protected/ReadFailure, persistence is disabled, source bytes remain byte-identical, and an Application save/shutdown cannot replace them.
- Add/retain a control proving a genuinely absent file remains `MissingFresh` and writable.
- Run test_config plus controller persistence regressions and the full Windows suite.

[P1] [W2-001] src/render/overlay_manager.cpp::OverlayManager::create / refresh_topology + src/app/application.cpp::display-change reconciliation

[P1] [W2-002] src/app/application.cpp::apply_start_with_windows / apply_app_config_transaction / save_config

- It then enables/disables the external per-user Run entry through AutostartManager.
- Only after the registry side effect does it call `save_config()`.

- `apply_app_config_transaction()` has the same ordering: install the new AppConfig, reconcile the Run entry at lines 979-989, then perform the single config persistence commit at line 992.

DEFECT:
The durable preference and machine side effect are a two-store transaction ordered in the unsafe direction. If disabling startup succeeds in the registry but the config write fails, disk still says `start_with_windows=true` while the Run value has already been removed. On the next Windows sign-in ProTrail does not start, so it cannot automatically perform the promised "next start" reconciliation until the user manually launches it. The inverse failure can create an unwanted autostart launch from a preference that never became durable. Whole-AppConfig operations have the same split-brain boundary.

- If registry reconciliation then fails, keep the durable desired preference and report the failure; a later launch/retry can converge machine state toward that durable authority.
- Route direct checkbox changes and whole-AppConfig transactions through the same helper so ordering cannot drift again.
- Preserve idempotent ON repair for moved executables and OFF cleanup for stale owned entries.
VERIFY:
- Add an Application-level deterministic config-save-failure seam.
- Starting from durable ON + registered Run entry, request OFF while config save is forced to fail; assert persisted preference remains ON and the backend receives no removal.
