PHASE 1 — EXPLICIT WINDOWS DPI CONTRACT

Establish an explicit process DPI-awareness contract before QApplication
or any top-level application window is created.

Target:

DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2

The contract must be established early enough that:

- GetCursorPos coordinates are physical virtual-desktop pixels;
- monitor RECT values are interpreted consistently;
- native overlay HWND coordinates are physical pixels;
- Qt Settings remains correctly DPI-aware.

Record success/failure truthfully.

Do not silently rely only on an undocumented Qt default.

If the API reports that DPI awareness has already been established,
determine the actual awareness context and verify it rather than blindly
calling another setter.

Add a diagnostic/helper that can prove the active process/thread DPI
awareness mode.

PHASE 2 — PRESERVE THE PHYSICAL-PIXEL COORDINATE INVARIANT

The architecture contract is:

CursorHistory:
virtual-screen physical pixels

TrailEffect / ClickBubbleEffect:
virtual-screen physical pixels

Per-monitor overlay:
physical-pixel monitor RECT

Render transform:

local_x = virtual_x - monitor_left
local_y = virtual_y - monitor_top

Do NOT multiply these coordinates by monitor scale.

Do NOT apply DPI scaling a second time.

Trail thickness, bubble radius and effect geometry currently use pixel
units and must remain internally consistent.

Make the D2D render-target DPI strategy explicit so one effect coordinate
unit continues to map predictably to one physical pixel.

If necessary, explicitly use a 96-DPI D2D coordinate surface for the
physical-pixel rendering contract rather than allowing an implicit target
DPI to introduce double scaling.

Document this invariant in the rendering code.

PHASE 4 — BIND MONITOR METADATA TO ITS OVERLAY

Current OverlayManager stores:

- monitors_
- overlays_

as separate arrays.

This becomes fragile when one overlay fails to create or topology changes.

Refactor narrowly so each live overlay is associated directly with the
MonitorInfo it represents.

A small internal record such as:

MonitorOverlay {
    MonitorInfo monitor;
    std::unique_ptr<OverlayWindow> window;
}

is acceptable.

Do not depend on two vectors remaining index-aligned after partial failure.

Preserve monitor device identity where useful for topology comparison.

PHASE 5 — DPI PER MONITOR

Track real DPI for each monitor/window.

Do not use a cached global/system DPI as the production authority.

After an overlay HWND exists, prefer window-specific DPI information where
available.

At minimum expose and record:

Mixed-DPI rendering must preserve the physical-coordinate invariant from
Phase 2.

again.

PHASE 6 — SAFE DISPLAY EVENT DELIVERY

Current OverlayWindow receives WM_DISPLAYCHANGE.

Do NOT call OverlayManager::refresh_topology() synchronously from inside
OverlayWindow::wnd_proc().

That can destroy the OverlayWindow whose wnd_proc is currently executing.

Required event contract:

WndProc
-> lightweight notification only
-> queue/defer topology reconciliation
-> return from WndProc
-> Application/manager performs reconciliation afterward

Use an existing Qt queued/event-loop mechanism or an equally small native
deferred mechanism.

Do not create a second polling loop.

Because WM_DISPLAYCHANGE is broadcast to multiple top-level windows,
coalesce duplicate notifications.

One physical topology change should schedule at most one pending topology
reconciliation.

Clear/unregister any callback during shutdown so no queued callback can
dereference destroyed Application state.

PHASE 7 — WM_DISPLAYCHANGE

Wire WM_DISPLAYCHANGE into the deferred reconciliation path.

When delivered:

1. mark topology refresh pending;
2. defer execution;
3. re-enumerate monitors;
4. compare topology;
5. create/remove/reposition required per-monitor overlays;
6. preserve correct overlays/resources where practical;
7. ensure removed-monitor windows are destroyed cleanly;
8. show new overlays without activation;
9. leave scheduler/input state valid.

Topology changes must not require application restart.

Do not recreate overlays synchronously inside WndProc.

PHASE 8 — WM_DPICHANGED

Add correct WM_DPICHANGED handling.

Do not treat DPI changes as equivalent to arbitrary numeric metadata only.

The notification must result in a safely reconciled overlay/window/render
state.

Handle the recommended bounds or replace the affected overlay through the
deferred topology path as appropriate for the architecture.

Do not double-scale:

- cursor coordinates;
- trail geometry;
- click geometry;
- thickness/radius values.

Ensure any swap-chain/render-target size affected by changed monitor
geometry is recreated or resized consistently.

PHASE 9 — TOPOLOGY RECONCILIATION

Required cases:

- monitor added;
- monitor removed;
- resolution changed;

Log the exact topology transition in diagnostic mode.
